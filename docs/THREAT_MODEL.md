# Модель угроз (Threat Model) — HEPRE

**Область.** Документ описывает модель угроз для протокола приватного скоринга риска
диабета 2-го типа, реализованного в настоящем репозитории (CKKS/BFV + решёточное
прокси-перешифрование INDCPA-PRE поверх OpenFHE; обёртка Rust через `cxx` bridge и C++-шим
`cpp/openfhe-shim.cc`).

**Статус.** Это исследовательский прототип. Ниже перечислены **только те** свойства, которые
следуют из конструкции и могут быть соотнесены с конкретным кодом и тестом этого репозитория.
Отдельным разделом (§7) явно указано то, от чего прототип **не** защищает. Формального
доказательства безопасности (model-checking, simulation-based proof) в репозитории нет:
криптографические гарантии наследуются от схем OpenFHE и здесь не доказываются заново.

Ссылки на источники: `README.md` (архитектура, PRE-конфигурация, границы FFI, ограничения),
`design.txt` (ТЗ и план статьи), `SECURITY.md` (политика безопасности и перечень известных
ограничений), `src/scoring.rs` (протокол A2), `src/bin/{lab,server,hospital}.rs`
(роли), `src/demo_common.rs` (файловый handoff), `cpp/openfhe-shim.cc` (FFI-слой),
`tests/` (интеграционные тесты). Этот документ — расширенная модель угроз; `SECURITY.md` —
краткая политика для пользователей и исследователей.

## 1. Обозначения и границы системы

| Термин | Значение в этом документе |
|---|---|
| Лаборатория (lab) | Владелец матрицы признаков `X` (`N × f`); шифрует признаки под своим открытым ключом и выпускает ключ перешифрования |
| Сервер (server / evaluator) | Считает `score_i = Σ_j w_j·x_ij + b` гомоморфно и выполняет `ReEncrypt` (PRE) |
| Прокси (proxy) | Сторона, выполняющая перешифрование. **В HEPRE прокси — это сам сервер**: отдельной четвёртой стороны нет |
| Больница (hospital) | Владелец `hosp.sk`; расшифровывает только финальный скор и применяет порог `threshold` в открытом виде |
| Handoff | Каталог `handoff/`, через который роли обмениваются **только файлами** (бинарь OpenFHE в контейнере `MAGIC`/version/kind, см. `src/demo_common.rs`) |
| Скор | Непрерывное значение `s_i` до порога (`score_i`) |
| Вердикт | Бинарный результат `s_i ≥ threshold`, вычисляемый больницей в открытом виде |

Схема потока (фактическая реализация A2):

```
Lab.KeyGen ──► Lab.Enc(features)         -> handoff/features.cts.bin  ──► server
Hosp.KeyGen ─► handoff/hosp.pk.bin       ──► lab
Lab.ReKeyGen(lab_sk -> hosp_pk)          -> handoff/rekey.ek.bin      ──► server
server: score = Σ w_j·ct_j + b  ──► ReEncrypt(rekey, score) -> handoff/scores.ct.bin ──► hospital
Hosp.Decrypt(scores.ct.bin) + threshold in the clear
```

В **исследовательском** контуре (`src/he.rs`, `src/study.rs`) поток тот же, но добавляются два
элемента: лаборатория выполняет стандартизацию `z = (x − mean)/sd` (средние и СКО — публичные
метаданные модели) и генерирует **ключ умножения** (`Context::evmult_keygen`) для многочленной
аппроксимации сигмоиды, а сервер, кроме логита, вычисляет многочлен от шифротекста и перешифровывает
**вероятность** на ключ больницы. Ключ умножения производен от `lab_sk` и публикуется серверу (актив
A9) — это стандартный элемент FHE-контура, стойкость которого здесь не проверяется.

Замечание о терминологии: в `design.txt` шаг назван `Hospital.ReKeyGen(lab_sk → hosp_pk)`, однако
реализация (`src/bin/lab.rs`) выполняет `rekeygen` **в процессе лаборатории** — это единственный
вариант, при котором `lab_sk` вообще не покидает лабораторию. Ниже используется фактическое
поведение кода.

Что **не** является частью системы: сетевой транспорт (роли обмениваются файлами, TLS/аутентификации
нет), сервис управления ключами, аутентификация пациентов, журнал аудита. Неявно предполагается,
что ОС и файловая система не скомпрометированы, а `vendor/` OpenFHE собран без вредоносных
изменений; аддитивные вендорные патчи перечислены в `README.md` (§«Вендорные патчи»).

## 2. Активы

| # | Актив | Где существует в открытом виде | Класс | Что означает компрометация |
|---|---|---|---|---|
| A1 | Матрица признаков пациентов `X` (`N × f`) | Только в процессе лаборатории (в демо-режиме больницы — см. §6) | Конфиденциально, персональные данные | Раскрытие лабораторных показателей пациентов |
| A2 | Производный скор `s_i` / вероятность и бинарный вердикт | Больница после расшифровки; сервер — нет | Конфиденциально (клинически значимо) | Раскрытие риска конкретного пациента |
| A3 | Веса модели `w`, интерцепт `b`, порог `threshold` | Публичны по построению: передаются лаборатории и серверу аргументом `--model` (`src/bin/lab.rs`, `src/bin/server.rs`); `design.txt` называет модель публичной | Публично (в прототипе), отдельного коммитмента нет | Сервер может подменить модель незаметно (см. §7) |
| A4 | `lab_sk` | Только в ОЗУ процесса лаборатории (`src/bin/lab.rs` его не сериализует) | Критично | Полная расшифровка всех шифротекстов лаборатории |
| A5 | `hosp.sk` | Файл `handoff/hosp.sk.bin` (бинарь OpenFHE, **без шифрования и пароля**) | Критично | Больница/атакующий расшифровывает всё, что перешифровано на её ключ |
| A6 | `rekey.ek.bin` = `ReKeyGen(lab_sk → hosp_pk)` | Файл `handoff/rekey.ek.bin` у сервера | Чувствительно: **правомочие transfer**, не правомочие расшифровки | Позволяет перевести **любой** шифротекст лаборатории (и любую их гомоморфную комбинацию) под ключ больницы. Сам по себе расшифровку не даёт |
| A7 | `hosp.pk` | Публичный | Публично | — |
| A8 | Корректность/целостность возвращённого результата | — | Актив, который **не защищён** | Больница принимает клиническое решение по подменённому скору |
| A9 | Ключ умножения (релинааризации) для схемы `s²`, выведенный из `lab_sk` и публикуемый серверу | Передаётся серверу (в исследовательском контуре `src/he.rs`; в A2-контуре не используется, там только `EvalMultPlain`) | Условно чувствительно | Не даёт расшифровки (стандартное допущение FHE: релинааризационный ключ не раскрывает `s`), но расширяет поверхность атаки: это дополнительный материал, производный от `lab_sk`, и его стойкость здесь **не проверяется** |

Производные от A1 данные (`cohort.csv` в планируемой раскладке `results/<run-id>/`, см.
`docs/REPRODUCIBILITY.md`) наследуют класс A1 **только для реальных данных**; в этом репозитории они
синтетические (см. `docs/DATA_DICTIONARY.md`), поэтому артефакты прогона (`cohort.csv`,
`model.json`, `results.json`) не содержат персональных данных. Их целостность обеспечивается
контрольными суммами SHA-256 (`src/hash.rs`, digest-ы в `manifest.json`), но не аутентификацией:
MAC/подписи нет.

Важно разделять два разных механизма целостности: SHA-256 применяется к **артефактам
исследования** (манифест и файлы `results/<run-id>/`), тогда как handoff-файлы ролей
(`features.cts.bin`, `scores.ct.bin`, ключи) аутентификации не имеют вовсе — см. §4.2 (M3) и §7 (O6).

## 3. Стороны и что каждая может узнать

| Сторона | Имеет | Может вычислить/узнать по протоколу | Чего узнать не может (при сделанных допущениях) |
|---|---|---|---|
| **Лаборатория** | `X` (открытый текст), `lab_pk`, `lab_sk` (эфемерный), `hosp_pk`, `rekey` | Всё о собственных данных; сам скор (может вычислить его и без HE, т.к. модель публична) | `hosp_sk`; содержимое перешифрованного на больницу шифротекста после PRE (однонаправленность `lab → hosp`) |
| **Сервер (= прокси)** | `features.cts.bin`, `rekey.ek.bin`, публичная модель; в исследовательском контуре дополнительно ключ умножения (`evalmult`, производный от `lab_sk`) и `eval_key`; ключей расшифровки нет | Размеры и число шифротекстов, `n` и `f` из заголовка контейнера, время работы; может выполнять произвольные аффинные комбинации шифротекстов (`EvalMultPlain`, `EvalAdd`, `EvalAddPlain`), а с ключом умножения — и умножение шифротекст на шифротекст | `X`, `s_i` — ни одного ключа расшифровки у него нет (`src/bin/server.rs` читает ровно два файла) |
| **Больница** | `hosp.sk`, `hosp.pk`, публичная модель, `scores.ct.bin` | Скоры `s_i` для пациентов, которые ей переданы, и производный вердикт (§6) | `X` (кроме демо-режима сверки), промежуточные величины, `lab_sk` |
| **Прокси** | Совпадает с сервером | То же, что сервер | То же, что сервер |
| **Внешний сетевой нарушитель** | Файлы handoff / канал между ролями (в текущем прототипе — каталог на диске) | Метаданные: число и размеры файлов, `n`, `f` (из размера и заголовка контейнера), тайминги; при активном вмешательстве — подмена файлов | Открытые признаки/скоры (данные зашифрованы); ключи расшифровки в канал не передаются (`lab_sk` вообще не пишется на диск) |

Доверительные допущения, лежащие в основе таблицы:

1. Лаборатория и больница **честны** (не отклоняются от протокола).
2. Сервер рассматривается в двух режимах: получестный (§4.1) и злонамеренный (§4.2).
3. Стороны **не сговариваются** между собой сверх модели. Отдельно отмечу: сговор
   «сервер + больница» выходит за модель и приводит к раскрытию A1 — это разобрано в §7.
4. ОС, файловая система, компилятор и библиотека OpenFHE не подконтрольны нарушителю;
   побочные каналы не рассматриваются (§7).

## 4. Модель нарушителя

### 4.1 Получестный («honest but curious») сервер, статическая коррупция

- **Возможности.** Следует протоколу в точности, но сохраняет все полученные данные (файлы
  `features.cts.bin`, `rekey.ek.bin`, публичную модель, метаданные, тайминги) и может
  выполнять над ними **произвольные вычисления** неограниченное время, используя вспомогательную
  информацию (публичные статистики, данные о пациентах из других источников).
- **Момент коррупции.** Статическая: множество коррумпированных сторон фиксировано до начала
  протокола, адаптивный выбор по ходу протокола не рассматривается.
- **Цель.** Нарушить конфиденциальность A1 и A2.
- **Считается недостижимым** (при допущениях §3 и стойкости OpenFHE): выучить признаки `X`,
  промежуточные величины или скор `s_i`.

### 4.2 Злонамеренный сервер (отклоняющийся от протокола) — **НЕ защищён**

Прототип не имеет ни доказательств корректности вычисления, ни аутентификации артефактов, поэтому
отклоняющийся сервер не детектируется. Конкретные сценарии:

| # | Отклонение | Последствие | Обнаружимо? |
|---|---|---|---|
| M1 | Подмена модели: использование других `w`, `b` (или добавление произвольного plaintext через `EvalAddPlain`) | Больница получает скор от **другой** модели; вердикт клинически неверен | Нет: у больницы нет ни исходных признаков, ни обязательства по модели |
| M2 | `ReEncrypt` **отдельных** шифротекстов признаков (`features.cts.bin`) вместо скора | Больница расшифровывает **исходные признаки** — ключ перешифрования не привязан к функции `Σ w_j·x_j + b` и переносит любой шифротекст лаборатории | Нет. Это самый острый сценарий: PRE здесь функционально-агностично, а получестная модель запрещает его только «по определению» |
| M3 | Правка заголовка контейнера (`n`, `f`, `n_blobs`) или содержимого blob-ов | Подмена/дублирование/усечение пациентов, перестановка строк | Нет: контейнер не аутентифицирован (нет MAC/подписи), проверяются только `MAGIC`, версия и границы (`src/demo_common.rs`) |
| M4 | Отказ в обслуживании: возврат мусорного/чужого шифротекста | `Decode`-ошибка → `Err` у больницы (`guard<>` → thread-local → `Err`) | Частично: отказ виден, но источнику не атрибутируется |
| M5 | Повтор (replay) ранее выпущенного `scores.ct.bin` | Больница принимает устаревший результат | Нет: nonce/свежести в формате handoff нет |

Практический вывод: **гарантии HEPRE сформулированы против получестного сервера**. Против
злонамеренного сервера конструкция не защищает; M2 дополнительно означает, что сговор
«сервер + больница» равносилен раскрытию A1 (см. §7).

### 4.3 Внешний сетевой нарушитель

- **Пассивный.** Наблюдает метаданные: число файлов, их размеры, `n` и `f` из заголовка
  контейнера, а также тайминги (сервер печатает время; `examples/bench.rs` измеряет
  Encrypt/Score/PRE/Decrypt). Размер `scores.ct.bin` позволяет оценить число пациентов.
  Признаки и скоры защищены шифрованием (A1, A2 недоступны).
- **Активный (MITM).** Может подменить/удалить/переиграть файл в handoff. Контейнер
  не аутентифицирован, поэтому подмена не детектируется → нарушение целостности (A8) и
  потенциально конфиденциальности через M2/M3. **Не защищено.**

### 4.4 Что предполагается, но не проверяется

- Отсутствие сговора сторон (кроме явно рассмотренного «сервер + больница» в §7).
- Честность больницы: она не передаёт `hosp.sk` третьим лицам и не публикует расшифрованные скоры.
- Отсутствие компрометации ОЗУ/диска/гибернации: ключи и открытые тексты не зануляются
  (нет zeroization), `hosp.sk.bin` лежит на диске в открытом виде.
- Корректность и «отсутствие закладок» в OpenFHE, cxx-bridge, clang-cl и MSVC-рантайме.

## 5. Утверждения безопасности, которые конструкция действительно поддерживает

| # | Утверждение | Механизм | Чем подтверждается |
|---|---|---|---|
| C1 | **IND-CPA секретность шифротекстов под ключом источника (лаборатории).** Сервер, получив `features.cts.bin`, не может отличить шифрование `X` от шифрования любой другой матрицы того же размера | CKKS (RLWE) в OpenFHE, параметры `batch_size = 8192`, `multiplicative_depth = 3`, `scaling_mod_size = 40` (`src/demo_common.rs`, `src/scoring.rs`) | Наследуется от OpenFHE. **Собственного теста IND-CPA в репозитории нет** (его нельзя построить интеграционным тестом). Косвенно: `encrypt_decrypt_roundtrip`, `public_key_usable_after_serialize`, `wrong_key_fails_or_garbage` |
| C2 | **IND-CPA секретность в целочисленном контрольном пути BFV** | BFV, `plaintext_modulus = 65537` (`tests/bfv.rs`) | `bfv_roundtrip_and_eval`, `bfv_secret_key_roundtrip_serialization`. Примечание: в сквозном скоринге A2 BFV **не участвует** |
| C3 | **Сервер никогда не держит секретный ключ больницы** | Разделение процессов и файлов: `src/bin/server.rs` читает только `features.cts.bin` и `rekey.ek.bin`; `hosp.sk.bin` пишет и читает только `src/bin/hospital.rs` | `role_utilities_end_to_end` (межпроцессный прогон трёх утилит через handoff). Это **архитектурная** гарантия (проверяется чтением кода), а не криптографическая: отдельного теста «сервер не читает sk» нет |
| C4 | **Ключ перешифрования сам по себе не даёт возможности расшифровки** | `ReKeyGen` выдаёт `EvalKey`, пригодный только для `ReEncrypt`; публичный API `src/lib.rs` не содержит операции расшифровки, принимающей `EvalKey` — расшифровка требует `SecretKey` | `pre_reencrypt_recipient_can_decrypt` (расшифровывает **bob_sk**, не `ek`), `pre_evalkey_serialization_roundtrip` |
| C5 | **Корректность перешифрования и скоринга:** получатель расшифровывает именно переданный скор, и он совпадает с открытой линейной моделью | `transfer_score` = `ReEncrypt`; аддитивный контур `EvalMultPlain + EvalAdd + EvalAddPlain` без `Rescale` | `end_to_end_score_and_pre_to_hospital`, `multiple_patients_in_one_batch`, `role_utilities_end_to_end`, `pre_reencrypt_recipient_can_decrypt` |
| C6 | **Fail-closed при чужом ключе:** дешифровка неверным ключом даёт либо неправдоподобный мусор, либо жёсткую ошибку `Decode` (не молчаливо неверный, но «правдоподобный» результат) | CKKS `Decode` бросает исключение при слишком большой ошибке аппроксимации; `guard<>` перехватывает C++-исключение, кладёт текст в thread-local и возвращает сентинель; Rust превращает сентинель в `Err` (`README.md`, §«Обработка ошибок»; `src/lib.rs::ok_vec`, `cpp/openfhe-shim.cc::guard`) | **`wrong_secret_key_cannot_read_transferred_score`** (`tests/score.rs`), `wrong_key_fails_or_garbage` (`tests/serialize.rs`) |
| C7 | **Устойчивость границы FFI:** C++-исключение не приводит к `std::terminate`/`abort`, а становится `Err` в Rust | `guard<>` + thread-local `g_last_error` + сентинельные значения; Rust-обёртки `ok_handle`/`ok_vec` | Все тесты, ожидающие `Err` на «плохих» входах, в первую очередь `wrong_key_fails_or_garbage`; исходная мотивация описана в `README.md` |
| C8 | **PRE сконфигурировано корректно** (не падает неопределённым поведением) | `cc->Enable(PRE)` и `parameters.SetPREMode(INDCPA)` — обязательная пара; зашито в `ctx_new_ckks`/`ctx_new_bfv` (`cpp/openfhe-shim.cc`), в `EnableAll` входит `PKE\|KEYSWITCH\|PRE\|LEVELEDSHE\|ADVANCEDSHE` | `pre_reencrypt_recipient_can_decrypt`, `pre_evalkey_serialization_roundtrip` |

Уточнения к C1/C6, важные для честности:

- C1 — это **IND-CPA**, а не IND-CCA. Любой оракул расшифровки (в т.ч. «попробуй расшифровать и
  посмотри, будет ли `Decode`-ошибка») выходит за модель; см. §7.
- C6 в тесте `wrong_secret_key_cannot_read_transferred_score` формулируется эвристически: либо
  `Err`, либо все полученные значения отстоят от ожидаемых более чем на `0.1`. Это **не**
  доказательство неотличимости, а инженерная проверка отсутствия «правдоподобного» мусора.
- C3/C4 опираются на API и разделение файлов; они не проверяются криптографически и не мешают
  злонамеренному серверу (M2).
- C5 относится к **сквозному** контуру A2: линейный скор в CKKS без `Rescale`, порог применяется
  больницей в открытом виде. Исследовательский контур (`src/he.rs`, `src/poly.rs`) приближает
  сигмоиду нечётным многочленом (схема Патерсона—Стокмейера, глубина из
  `poly::select_evaluation_scheme` проверяется против `multiplicative_depth`) и переносит бинарное
  решение на знак логита (`η ≥ 0`); для умножений «шифротекст на шифротекст» требуется ключ
  умножения из `Context::evmult_keygen` (актив A9), который публикуется серверу. На момент написания
  этот контур объявлен в `src/lib.rs`, но не покрыт интеграционными тестами A1/A2.

## 6. Что больница узнаёт **по построению**

Это не утечка ошибки, а свойство самого протокола: больнице выдан результат функции от данных.

1. **Точный скор `s_i`** для каждого пациента, который ей передан (расшифровка первых `k` слотов
   пакета, `decrypt_scores`). Больница получает именно непрерывное значение, а не только вердикт.
2. **Бинарный вердикт** `s_i ≥ threshold`, который она вычисляет сама в открытом виде. Поскольку
   `threshold` публичен, вердикт — детерминированная функция от `s_i` и **не добавляет** новой
   информации; избыточным является как раз выдача непрерывного скора.
3. **Одно линейное уравнение на пациента.** Для линейной модели
   `s_i = Σ_j w_j·x_ij + b` со **известными** `w` и `b` знание `s_i` фиксирует одну линейную
   комбинацию признаков. Верхняя граница утечки на пациента — одно вещественное число (плюс
   детерминированный от него бит вердикта). Практические следствия:
   - если хотя бы `f − 1` признаков пациента известны из другого источника, оставшийся признак
     вычисляется **точно** (линейное уравнение с одним неизвестным);
   - в общем случае неопределённость входа сжимается до аффинной гиперплоскости размерности `f − 1`;
   - при наличии априорных распределений признаков (публичные популяционные статистики) каждый скор
     уточняет апостериорное распределение; величина уточнения зависит от модели и признаков и здесь
     намеренно не оценивается численно.
4. **Относительный порядок пациентов.** Больница видит `s_i` для всей переданной когорты, то есть
   ранжирование по риску (кто выше/ниже), даже если абсолютные значения ей не нужны.
5. **Размер когорты и состав пакета.** `n` берётся из заголовка контейнера, порядок пациентов —
   порядок слотов.
6. **Погрешность CKKS.** Числа, которые видит больница, отличаются от точного значения открытой
   модели на шумовую компоненту порядка `10⁻⁹` (величина приведена в `README.md` как ориентир;
   она случайна от прогона к прогону). Этот шум не меняет класс утечки, но означает, что скор
   больницы — не «идеальное» значение функции.

Отдельно: демонстрационный режим `hospital decrypt --patients …` (`src/bin/hospital.rs`) передаёт
больнице **открытые признаки** для сверки точности и печатает `max|err|` и число расхождений с
порогом. Это **только демонстрация**: в реальном развёртывании больница не должна получать
`--patients`, иначе свойство §6(1) деградирует до полного раскрытия A1. Аналогично, `README.md`
явно оговаривает, что `--patients` нужен лишь для сверки.

## 9. Допущения, которые прототип не проверяет (сводка)

1. Криптографическая стойкость OpenFHE CKKS/BFV/INDCPA-PRE и выбранных параметров.
2. Получестность сервера. Все privacy-гарантии против сервера опираются на **это** допущение;
   злонамеренный сервер (§4.2) — вне модели.
3. Отсутствие сговора «сервер + больница» (O7).
4. Честность больницы и защищённость файла `hosp.sk`.
5. Защищённость канала handoff (файловая система, права доступа) и отсутствие MITM.
6. Отсутствие побочных каналов и оракулов расшифровки.
7. Отсутствие закладок/дефектов в цепочке сборки (clang-cl, MSVC-рантайм, вендорные патчи OpenFHE).
